# AI 图片理解与查询 V3 设计

## 1. 目标与范围

V3 分两个阶段实施：

1. **阶段 A：图片与相册理解**。直接使用支持视觉输入的大模型，逐张、可恢复地分析照片，并生成可检索的结构化事实、描述、标签和语义向量。
2. **阶段 B：查询 V3**。在阶段 A 的数据之上，实现自然语言、布尔组合、跨照片分析、多轮追问和证据化回答。

本阶段只实现阶段 A，不把查询逻辑和视觉识别耦合在一起。模型负责理解，数据库负责保存和后续查询。

## 2. 为什么直接使用大模型

几千张照片且不要求立即完成时，可以采用后台串行任务调用视觉大模型。优点是开放式描述、行为、关系和记忆点质量更高，开发复杂度也低于维护多套本地模型。

模型必须支持图片输入（Vision/VL）。纯文本模型不能识别图片。具体模型通过统一适配器接入，首选具备稳定视觉 API 的模型；DeepSeek、GPT、Qwen-VL 等均可作为实现选项，实际选择以账号可用性、图片输入能力、中文质量、成本和隐私策略为准。业务代码不得绑定某一家模型的返回格式。

## 3. 单张照片分析结果

建议新增独立的 `photo_ai_analysis` 数据模型，不把所有内容继续堆入 `photo` 表的单个 JSON 字段。

```json
{
  "photoId": 123,
  "schemaVersion": "v3",
  "caption": "两个人沿溪边散步，周围是树林和山石",
  "objects": [{"name": "人物", "confidence": 0.98}],
  "actions": [{"name": "散步", "confidence": 0.82}],
  "scenes": ["户外", "自然", "旅行"],
  "moods": ["安静", "轻松"],
  "memoryPoints": ["两人同框", "溪流", "春季氛围"],
  "textInImage": [],
  "visualTags": ["溪流", "树林", "同行", "春天"],
  "estimatedTimeOfDay": "afternoon",
  "locationCandidates": [{"name": "杭州九溪烟树", "confidence": 0.78}],
  "personSignals": [{"personId": 12, "role": "person", "confidence": 0.91}],
  "qualitySignals": {"composition": 0.78, "technical": 0.82},
  "embeddingRef": "photo_embedding:123",
  "evidence": [{"field": "locationCandidates", "source": "folder_name_and_visual"}],
  "model": "provider/model-name",
  "modelVersion": "...",
  "confidence": 0.86,
  "status": "completed"
}
```

字段应分为四类：

- **观察事实**：物体、文字、场景、动作、颜色、时间段。
- **语义描述**：caption、氛围、记忆点、候选标签。
- **推断结果**：地点、事件、人物关系，必须带置信度和来源。
- **运行元数据**：模型、版本、提示词版本、耗时、状态和错误。

模型输出先经过 JSON Schema 校验、枚举归一化和长度限制，再入库。原始响应可保存到对象存储或审计表，结构化结果用于查询。

## 4. 文件夹与相册理解

相册分析应综合以下证据：

```text
文件夹名称 + 文件名 + EXIF 时间/GPS + 照片视觉标签 + 人物统计 + 日期分布
```

文件夹名（如 `2025-九溪烟树-春游`）只能产生地点和主题候选，不能覆盖真实 GPS 或用户确认。相册结果应包含：

- 标题和简短描述
- 日期范围
- 地点候选及证据来源
- 主题、人物、场景和活动统计
- 文件夹名与视觉内容冲突提示
- `confirmed / inferred / possible / unknown` 状态

相册摘要应在照片分析完成后生成，输入使用压缩后的标签和代表性样本，不把整本相册原图一次性发送给模型。

## 5. 串行任务与可恢复性

沿用现有人脸、场景分析的后台处理思路，新增独立的 `PhotoAiUnderstandingJob`：

1. 按用户和照片 ID 领取任务，一次处理一张。
2. 状态：`PENDING -> RUNNING -> COMPLETED / FAILED / RETRY_WAITING`。
3. 记录尝试次数、下次重试时间、模型版本和错误原因。
4. 使用幂等键 `photoId + schemaVersion + modelVersion`，重复执行不会产生重复结果。
5. 支持暂停、继续、单张重试、批量重算和模型升级后的增量重算。
6. 对限流、超时、服务不可用使用指数退避；单张失败不阻塞整个队列。

初期可以使用定时任务或管理端手动触发，不要求引入重量级消息队列。任务处理必须在事务边界内更新状态，避免进程重启后永久停留在 `RUNNING`。

### 5.1 后台概览与任务控制

视觉分析必须在后台概览中显示独立卡片，不能与扫描、缩略图、人脸或 ONNX 评分任务混为一谈。卡片至少展示：

- 总照片数、已完成、跳过、失败、待处理数和完成百分比
- 当前处理照片（仅展示安全的文件名/相册名）、开始时间、预计剩余时间和模型名称
- 最近错误及下一次重试时间
- API 配置是否就绪、视觉分析开关状态、最近一次完成时间
- 暂停、继续、重试失败项、单张重试、增量重跑和按模型/提示词版本重跑入口

进度应从持久化任务记录读取，而不是只存在内存中；服务重启后，运行中的任务需自动标记为可恢复状态。管理端轮询独立的视觉分析任务状态接口，默认 2 至 5 秒刷新一次，任务完成后停止轮询。

所有耗时模型能力应统一纳入“模型作业”总览：扫描、人脸检测/聚类、缩略图、ONNX 评分、背景移除、相册氛围与视觉大模型分析各有独立进度，同时由超管概览汇总队列数、运行数、成功/失败数、总吞吐和最近错误。每类作业都设置独立并发和资源预算；视觉大模型允许多线程，但默认低并发（建议 1 至 2），并受提供商限流、每日预算和退避重试控制，避免阻塞本地扫描与人脸任务。

## 6. 大模型调用约定

统一 `VisionModelProvider` 接口，至少包含：

- `analyzePhoto(image, metadata, promptVersion)`
- `summarizeAlbum(albumContext, sampleImages, promptVersion)`
- `healthCheck()`

提示词要求模型返回严格 JSON，不返回 Markdown。图片发送前使用缩略图和尺寸上限；原图只在低置信度或必要时重试。请求中不包含无关用户数据。

提供商配置应支持 URL、模型名、密钥、超时、并发数和每日预算。密钥只保存在服务端配置中，日志不得记录图片内容和密钥。

### 6.1 配置权限与迁移

AI API 地址、密钥、模型、全局开关、并发数和预算是**平台级配置**，必须只在超级管理员后台维护。当前 AI 搜索配置虽然从普通用户“设置”页进入，但实际保存在全局 `system_config`，因此应迁移其界面入口和 API 权限：

1. 超管后台新增“AI 提供商与模型作业”页，统一管理搜索和视觉分析的共享提供商配置。
2. 所有读取真实密钥、写入配置、发起全局批处理的接口都必须校验 `SUPER_ADMIN`；响应中的密钥始终脱敏。
3. 普通用户设置页移除 API 地址、密钥和模型字段，不应让用户误以为配置隔离。
4. 若未来开放用户自带密钥，必须新建按 `user_id` 隔离的 provider 配置，并明确计费、额度、数据边界和优先级，不能复用全局密钥字段。
5. 普通用户只保留个人层面的“是否允许对我的照片使用 AI”“查看自己的任务进度”“取消自己的任务”等权限。

## 7. 置信度、证据与人工修正

视觉模型会误判，V3 不把推断写成绝对事实。每个可查询字段都应记录：

- 值
- 置信度
- 来源（EXIF、文件夹名、文件名、视觉模型、用户确认）
- 是否已确认
- 生成模型和版本

用户修正优先级高于模型推断，但不覆盖原始结果；保留修正历史，便于回滚和评估。

## 8. 为查询 V3 预留的数据接口

阶段 A 结束后，查询层可以把视觉结果作为受控数据源接入 V2 的 Planner/Validator/Executor：

- `filter_ai_tags`
- `filter_objects`
- `filter_actions`
- `filter_scene`
- `filter_mood`
- `filter_text_in_image`
- `filter_location_candidates`
- `semantic_photo_search`
- `find_similar_photos`
- `aggregate_album_semantics`

查询执行仍采用“结构化过滤 + 语义向量召回 + 融合重排 + 证据归约”。模型不能直接生成 SQL，也不能在查询时临时猜测照片事实。

## 9. 专业摄影分析与字段演进

大模型可以增强现有标签和评分，但不应简单覆盖旧字段。V3 采用“原始事实、机器测量、专业审美、用户评价”四层模型：

1. **原始事实**：EXIF、宽高、文件大小、拍摄时间、原始文件名，永远以程序读取结果为准。
2. **机器测量**：清晰度、曝光、噪声、对比度、主体位置等，可由专用模型或图像算法计算。
3. **专业审美**：构图、光线、色彩、主体表达、叙事性、情绪、封面适配度，由大模型按固定评分标准评估。
4. **用户评价**：精选、喜欢、隐藏、人工标签和人工评分，优先级最高且独立保留。

### 9.1 专业评分建议

不要只生成一个不可解释的总分。建议保存分项分数、理由、适用场景和置信度：

```json
{
  "scores": {
    "composition": 82,
    "lighting": 76,
    "color": 88,
    "subject": 84,
    "storytelling": 79,
    "technical": 73,
    "coverSuitability": 86
  },
  "overall": 81,
  "style": "旅行纪实",
  "strengths": ["主体关系清晰", "色彩统一"],
  "weaknesses": ["高光略有溢出"],
  "improvementSuggestions": ["裁剪顶部空白", "适当降低高光"],
  "rubricVersion": "photo-critic-v1",
  "confidence": 0.81
}
```

评分必须绑定 rubric 版本。不同模型、提示词或评分标准产生的分数不能直接混排；重算时保留旧版本，查询层明确当前使用的评分版本。总分应由分项分数按固定权重计算，不能完全交给模型自由决定。

可以提供有限的评价视角，而不是让模型假装真实摄影师：

- `documentary`：纪实与信息完整性
- `fine_art`：形式、光线和视觉表达
- `portrait`：人物关系、姿态和情绪
- `travel_editorial`：地点特征、叙事和旅行记录价值
- `social_cover`：缩略图可读性和封面适配度

同一张照片可以有多个视角分数，但必须明确视角名称。系统不应声称“某位真实摄影师评价了这张照片”，而应称为“按纪实摄影评价标准分析”。

### 9.2 标签治理

标签建议拆为三种：

- **标准标签**：从受控词表中选择，可用于精确过滤，例如“溪流”“夜景”“旅行”。
- **开放标签**：模型发现的长尾描述，保留原词和归一化词，例如“沿溪边行走”归一为“散步”。
- **关系标签**：人物同框、牵手、拥抱、多人聚会等，需要保存参与者和置信度。

标签应记录 `source`、`confidence`、`normalizedValue` 和 `taxonomyVersion`。低置信度标签默认只用于语义召回，不直接作为强过滤条件；用户确认后才升级为确定标签。

### 9.3 建议输出

除“这是什么”外，分析结果可以提供可执行建议：

- 是否适合精选或作为相册封面
- 推荐裁剪方向和展示比例
- 建议补充的标签
- 可能重复或相似的照片
- 需要人工确认的人物、地点和事件
- 相册中缺失的关键时间段或主题

建议必须标记为 `suggestion`，不能伪装成事实，也不应自动修改用户数据。批量采纳建议前应提供预览和撤销能力。

## 10. 视觉关系与人物绑定

图片理解和人物身份识别应当解耦。视觉模型先记录“画面中存在两个或多个匿名人物及其关系”，人脸识别或用户确认完成后，再把匿名主体绑定到 `personId`。

单张照片可以保存关系事实：

```json
{
  "relation": "hugging",
  "participants": [
    {"subjectId": "person-slot-1", "personId": 12, "confidence": 0.94},
    {"subjectId": "person-slot-2", "personId": 27, "confidence": 0.89}
  ],
  "context": ["sunset", "outdoor"],
  "observers": [{"type": "dog", "action": "watching", "confidence": 0.76}],
  "confidence": 0.84,
  "source": "vision_model"
}
```

关系查询必须支持以下状态：

- 两个已绑定人物：`A 和 B 拥抱`
- 一个已绑定人物、另一个匿名人物：`A 和谁拥抱`
- 完全匿名关系：`两个人拥抱的照片`
- 关系与环境组合：`夕阳下 A 和 B 拥抱，旁边有狗`

绑定发生后不需要重新识别整张照片。系统只需重新计算关系参与者的身份引用，并保留视觉模型原始的匿名主体和置信度。若用户解除绑定，查询应自动退回匿名状态。

人物关系不能只存一段描述文本，至少需要标准关系类型、参与主体、方向性、置信度和证据区域。首批关系类型可以包括：`hugging`、`holding_hands`、`kissing`、`talking`、`walking_together`、`looking_at`、`sitting_together`、`grouping`。开放式关系描述保留为扩展字段，经过人工确认后再加入受控词表。

## 11. 模糊记忆式查询

V3 应支持用户只记得片段的自然语言查询，而不要求准确的人名、标签或文件名。例如：

> 我记得有张照片是夕阳下 A 和谁拥抱，旁边还有只狗在看的来着

这类查询应被解析为多个软条件和一个待补全变量：

```text
核心事件：拥抱
已知人物：A
未知人物：一个共同参与者
环境：夕阳 / 户外
旁观主体：狗
用户语气：记忆不确定，允许近似匹配
```

执行时采用“硬条件 + 软条件 + 语义召回”的混合策略：

1. 先用关系类型和已绑定人物缩小候选集。
2. 使用场景、物体、动作和 caption 向量召回“夕阳”“狗”“观看”等近义表达。
3. 对候选照片按关系匹配、人物匹配、环境匹配和视觉相似度重排。
4. 返回最相关照片，并明确哪些条件命中了、哪些只是近似。
5. 若“谁”是未知变量，从关系记录中反推出共同参与者并展示候选人物。

回答示例应类似：

> 找到 3 张接近的照片。最匹配的是 2025 年九溪烟树相册中的一张：A 与 B 拥抱，画面右侧有一只狗，背景为夕阳。 “观看”是视觉模型的近似判断，置信度 0.76。

不能因为只命中了“拥抱”和“狗”就声称完全找到了用户记忆中的照片。结果应包含匹配度、证据字段和“可能不是同一张”的保守提示。

## 12. 批量 AI 整理与批量调整

图片理解完成后，可以提供只读预览、用户确认、可撤销的批量操作。AI 先提出计划，系统展示影响范围，用户确认后才写入。

适合的批量整理包括：

- 为一批照片补充或归一化标签
- 按视觉主题建议相册分组
- 生成相册标题、描述和地点候选
- 识别疑似重复照片并保留最佳照片建议
- 找出低置信度的人物、地点和关系供人工确认
- 批量生成精选候选、封面候选和排序建议
- 将“旅行、家庭、活动”等主题写入用户可编辑的分类

批量调整计划应包含：

```json
{
  "operation": "apply_tags",
  "scope": {"photoIds": [1, 2, 3]},
  "changes": [{"add": "夕阳"}, {"remove": "夜景"}],
  "reason": "视觉内容与文件夹上下文一致",
  "confidence": 0.88,
  "requiresConfirmation": true,
  "rollbackToken": "..."
}
```

所有批量写操作必须具备预览、差异展示、审计记录、幂等键和撤销能力。模型不得直接执行删除、覆盖原图、改变人物绑定或修改用户确认结果；这些操作必须经过更高等级的明确确认。

## 13. 评估与专业性保障

V3 需要建立真实照片样本集和人工标注集，分别评估：

- 物体、动作、关系和 OCR 的准确率
- 人物绑定后的关系查询准确率
- 地点候选的命中率和误报率
- 专业评分与人工摄影评价的一致性
- 模糊记忆查询的 Top-K 找回率
- 批量建议的采纳率和撤销率

模型升级、提示词升级或标签词表升级后，必须用固定样本回放比较，不应只凭演示照片判断效果。对于人物、地点和敏感属性，宁可返回“无法确认”，也不要生成确定性结论。

## 14. 验收标准

阶段 A 至少应满足：

1. 可对单张照片完成分析、重试和结果查看。
2. 批量任务可暂停、恢复，重启后不会丢失进度。
3. 结构化结果可按标签、动作、场景、地点候选和描述检索。
4. 每个推断字段有来源和置信度。
5. 相册可生成描述，并能指出文件夹名与照片内容的冲突。
6. 更换模型或提示词后可以增量重算，不破坏旧版本结果。
7. 没有视觉分析结果时，旧的文件名、EXIF、人脸和普通筛选功能继续可用。

## 15. 实施顺序

1. 定义 schema、实体、Repository 和模型适配器。
2. 实现单张照片分析 API 与管理端状态展示。
3. 实现可恢复的串行批处理任务。
4. 实现结果校验、归一化、置信度和审计记录。
5. 实现相册级摘要与地点候选合并。
6. 生成图片 embedding 并建立向量存储接口。
7. 用真实数据评估后，再开始查询 V3 的 DSL、混合检索和多轮会话。

查询 V3 的详细执行架构继续参考 [ai-search-architecture-v2.md](ai-search-architecture-v2.md)；本文件定义的是视觉理解数据层和阶段边界。
